### Code PR Guide

- If any one of the team member have been working in any **feature** update, that member should build them in a separate branch in the following pattern `feature/feature-id` this feature can be tabulated in **project-01-spr** spreadsheet under features worksheet with all the requirements made already been documented.

- Also, when there is a **bug** is found in the **dev branch** team must create a separate branch for that particular bugfix in the following pattern `bugfix/bug-id` so the bug id needs to be also documented in the **project-01-spr** under the bugs worksheet with all the points need to be fixed.

- After the member feels like all the requirements related to the particular feature taken is completed and tested for code coverage and code smell. Developer will take his **local branch** to the **remote repo**.

- Then having a **PR Discussion** the team will together work on the improvements and modifications. As of reference for all the future **PR Discussion** points which are discussed in the PR will be taken into record in the **CODE QUALITY** notes by individual members of the team.

- After all this things finally the **PR** will be decided on whether it is need to be **added/merged** to the **dev branch.**

### Release Note guide

After all the specified features and bug related to them were fixed as per the **project-01-spr** is marked as working/completed then a release note for what are implementations we have completed in the a **release note** in with all the actions and flows being implemented into the application on the basis of releases and updating the application. Example: Release Note file will be named in the following pattern `Release 0.x.x` and those x can be any number of the release note. Finally after implementing the features freezed for the application then `Release x.0.0` will be released as production grade release note.
